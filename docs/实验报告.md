# 实验报告：七种图像变化检测方法的判定与耗时对比

> 配套项目：`image-diff-lab`（一个接口 + 七个实现类 + AOP 计时切面）
> 实验日期：2026-11-05　环境：Windows / Python 3.10.11 / OpenCV 4.10 / Ultralytics 8.4 / PaddleOCR 3.7
> 模型：YOLO 权重需自备（BYOM，见 `docs/yolo-byom.md`）；OCR `PP-OCRv5_mobile_det/rec`（CPU）

## 一、实验目的

输入两张微信截图（例如“联系人旁有红点”与“红点消失”），用七种方法分别判断：

1. 两张图之间是否发生变化；
2. 变化属于新增、消失、位置变化，还是仅内容变化；
3. 变化发生在哪些区域；
4. 每种方法从函数进入到返回实际耗时多少（由 AOP 切面统计）。

重点不是选出“最强方法”，而是观察**每种方法看得见什么、看不见什么、代价多大**。

## 二、实验设计

### 2.1 单次对比

本实验按需求只做**单次图对对比**：

- 前端上传两张图；
- 后端一个接口 `POST /api/compare` 依次调用七种方法；
- 输出统一结构，不做数据集训练，也不声称统计准确率。

没有真值时无法计算准确率。页面给出的是每个方法的**判定 + 置信度**，以及方法之间的**一致度**。
置信度是方法内部证据强度，不等于“在数据集上对了多少”。

### 2.2 内置示例对

从真实微信截图上人工构造 4 组图对，红点位置/类型已知，仅用于演示和冒烟验证：

| 图对 | 构造 | 期望 |
| --- | --- | --- |
| 红点新增 | 基准图 → 第一个联系人头像右上角画红点 | 发现变化，类型“新增” |
| 红点消失 | 有红点 → 擦除红点 | 发现变化，类型“消失” |
| 红点移位 | 第一个联系人有红点 → 第三个联系人有红点 | 发现变化，类型“位置变化” |
| 无变化 | 同一张图复制两份 | 判“无变化”，观察误报 |

> 示例由 `tools/make_samples.py` 生成；红点是无数字的纯色圆，避免 OCR 把数字当成文本变化。

## 三、七种方法

| # | 方法 | 实现要点 | 输出语义 |
| --- | --- | --- | --- |
| 1 | OpenCV 图像差异 | 灰度绝对差 → 阈值 22 → 形态学开运算/膨胀 → 连通域 | `hasChange` + 区域框；类型只能给 `content` |
| 2 | HSV 红色检测 | HSV 双区间红掩码（H≤10 / H≥168）→ 面积/长宽比/填充度过滤 → 前后色块配对 | 能给出 `added / removed / moved / none` |
| 3 | SSIM | 11×11 高斯窗口，亮度/对比度/结构三项；阈值 0.995 | 整体是否变化；对局部小目标不敏感 |
| 4 | OCR | PaddleOCR 识别两图文字；精确文本 + 同位置模糊匹配（相似度≥0.85）过滤识别抖动 | 文本新增/消失；红点等非文字元素不可见 |
| 5 | YOLO | 自定义微信 UI 模型框出元素；同类目标 IoU 配对；比较同一元素前后裁剪的像素差 | 能定位“哪一个 UI 元素内部变了” |
| 6 | 灰度指纹差分 | dHash / aHash / pHash 三种感知哈希；另算 16×16 分块灰度差用于粗定位 | 是否仍是“同一画面”；红点等局部小改会被缩图抹平 |
| 7 | ORB 特征对齐差分 | ORB 特征 + BFMatcher + RANSAC 单应性；后图 warp 到前图坐标系后比较残差 | 先判断整体平移/滚动，再看残差；纯位移判“无内容变化” |

七种方法都实现同一个抽象类 `ChangeMethod.detect(before, after) -> MethodResult`，
业务代码不自行计时。

## 四、统一输出契约

```text
MethodResult
├─ key / name / ok / error
├─ elapsedMs                 ← AOP 在方法返回时写入
├─ hasChange                 ← 是否变化
├─ changeType                ← none | added | removed | moved | content | unknown
├─ confidence                ← 0–1，方法内部置信度
├─ summary                   ← 一句结论
├─ regions[]                 ← 证据区域（对齐后画布像素坐标）
├─ metrics[]                 ← 页面直接展示的指标
├─ details{}                 ← 原始值（阈值、红点列表、OCR 行、YOLO 框）
└─ overlay                   ← 已画好证据的 JPEG data URL
```

接口还返回 `images`（原始尺寸/缩放/对齐信息）、`consensus`（多数投票与一致度）和
`timing`（服务总耗时、各方法耗时、AOP 切面记录）。

## 五、AOP 计时

`core/aspect.py` 用动态代理实现 Spring AOP 的 `@Around`：

- pointcut：`execution(*.detect(..))`，正则 `\.detect$`；
- 服务启动时扫描每个方法实现类，把 `detect` 替换为计时代理；
- `perf_counter_ns()` 在进入时打点，`finally` 在返回/异常时结算；
- 服务入口 `CompareService.compare` 也套同一层，得到 `totalMs`；
- 记录内容包括 `seq / traceId / target / startedAt / elapsedMs / status / thread`，
  页面底部和 `GET /api/traces` 均可查看。

因此：

```text
totalMs ≈ Σ 各 detect 的 elapsedMs + 解码/对齐/调度开销
```

## 六、实验结果（本机观察值）

`tools/selftest.py` 运行 4 组示例、7 种方法，以下为一次代表性结果：

| 红点消失 | 变化 / content / 25 ms | **消失** / 34 ms | 未变化 / 120 ms | 未变化 / 10.2 s | 变化 / 34 ms | 未变化 / 26 ms | 变化 / 48 ms |

## 七、结果分析

### 7.1 判定能力

- **像素差分**：4 组图对的“是否变化”全部判对；能给出精确区域框；但类型只能是“内容变化”，
  无法区分新增/消失。它是定位主力，不是语义判据。
- **HSV**：4 组全部判对，且唯一能直接给出“新增 / 消失 / 位置变化”的方法；
  在“红点”这个特定场景里最贴合。局限是只认红色，红色头像/红包等会进入候选
  （两张图中不变的红块会配对忽略）。
- **SSIM**：对三组红点变化都判“无变化”，对无变化组判“无变化”。这不是实现错误，
  而是全局指标把局部 100 多像素的差异平均掉了；它适合整体布局、滚动、主题切换。
- **OCR**：同样对三组红点变化判“无变化”。红点不是文字；它适合联系人名、消息、时间等
  文本变化。为了避免 OCR 自身的字形/标点抖动造成误报，比较时做了同位置模糊匹配。
- **YOLO**：4 组“是否变化”全部判对，并能把变化缩到具体 `session_item` 元素；
  但红点不是独立类别，类型仍只能给“内容变化”，需要 HSV/人工补充语义。
- **灰度指纹**：对三组红点变化都判“无变化”，因为缩到 8×8/32×32 后红点被抹平；
  它能快速判断“是否同一画面”，但对整图平移会报变化（测试中 pHash 距离 7 位），
  所以“指纹变了”不等于“内容变了”。
- **ORB 对齐**：对三组红点变化都判“变化”，对无变化组判“无变化”；
  额外构造整图平移 25px / 12px 后，ORB 用 571 个内点估计出 (-24.9, -11.9) 的位移，
  对齐后判“无内容变化”。这正是它相对普通像素差分的核心价值。

### 7.2 耗时

- 像素差分、HSV、灰度指纹都在**几十毫秒**级；SSIM 约 **0.1 秒**；
  ORB 约 **50 毫秒**；YOLO 在 GPU 上约 **几十毫秒**。
- OCR 是明显的瓶颈：CPU 上单张 **约 10 秒**，一次对比要跑两张；首次还要加载模型。
  如果实验重点是 OCR，建议换 GPU 版 Paddle 或更小的识别模型，或把 OCR 做成可选开关。
- 七种方法串行执行，总耗时近似等于各方法之和。串行是为了避免 OCR / YOLO / ORB
  争抢 CPU/GPU 导致每个方法的“自身耗时”失真。

### 7.3 一致度

页面上的“方法一致度”是多数投票结果（例如 4/7），表示方法之间的看法是否一致，
**不是准确率**。在红点场景里，SSIM / OCR / 指纹的“无变化”与另外四种方法的“变化”
会让一致度下降，这恰好暴露了方法的适用边界。

### 7.4 还可以考虑的方法

- **Lab ΔE 颜色差分**：亮度接近、只改颜色的状态（红→绿、置灰/高亮）。与灰度差分互补，
  也是我建议的下一个补充方法。
- **模板匹配 / NCC**：判断某个图标/按钮是否“移动了”，而不只是“变了”；适合元素级位移。
- **光流（Farneback）**：滚动、动画、连续帧的位移场；单张截图对之间意义有限。
- **直方图 / 颜色分布**：整体色调、主题切换、滤镜变化；定位能力弱。
- **Siamese U-Net / ChangeFormer**：像素级变化分割，精度上限最高，但需要训练数据和权重，
  超出本次“实现类横向对比”的范围。

## 八、结论

1. 对“微信联系人的红点变化”这一具体任务，**HSV 红色检测**是语义最直接、速度也足够快的方法；
   **OpenCV 像素差分**负责精确定位；两者组合最实用。
2. **SSIM**、**灰度指纹** 和 **OCR** 不应作为红点变化的主判据，它们分别适合整体结构、
   画面级去重和文本内容；在本实验里稳定地“看不见”小红点，符合预期。
3. **YOLO** 的价值在于把变化定位到具体 UI 元素，适合复杂界面；但需要额外的颜色/语义规则
   才能回答“新增还是消失”，且模型框外区域会漏检。
4. **ORB 对齐** 是应对“截图窗口挪动/页面滚动”的关键补强：先估计整体变换，再比较残差，
   可以避免普通像素差分把整屏位移误报成内容变化。
5. **AOP 切面**把计时从业务代码里彻底剥离：新增方法只要命名为 `detect` 就自动被计时，
   且能同时得到单方法耗时与服务总耗时。
6. 若要进一步得到“准确率”，需要引入带真值的图对集合，并在 `CompareService` 里对比
   `hasChange/changeType` 与 `truth`；当前版本按需求只做单次对比。
